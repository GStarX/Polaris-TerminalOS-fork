### K0-02：运行 config 对比判据（待设备/产物）

1. 构建机固定 `repo manifest -r` 与各仓 `git rev-parse HEAD`，保留 `out/.../.config`、构建日志、clang `--version`、`boot.img`/`dtbo.img`/模块清单和 SHA-256；仅有源码 `polaris.config` 不能代替展开后的 `.config`。
2. Phase 0 由首席核验设备与镜像归属后，采集 `uname -a`、`/proc/config.gz`（若不存在，记为不可用，不臆造替代来源）以及经校验来源的 boot/DTBO 镜像信息；任何读取设备的命令只由首席执行，Phase 0 前禁止刷写。
3. 用同一构建 commit 的展开 `.config` 对比运行配置，输出 `CONFIG_*` 的新增/缺失/值变化与采集来源；再比对 `boot.img` header、DTB/DTBO、模块 `vermagic`。若运行系统并非该构建，标记为“不同基线，不能归因”。

### K0-03：主线内核的 polaris 设备树（2026-10-28，只读核验）

| 项 | 已核验结论 | 证据 |
| --- | --- | --- |
| 主线设备树存在 | `arch/arm64/boot/dts/qcom/sdm845-xiaomi-polaris.dts` 存在于 mainline；`model = "Xiaomi Mi MIX 2S"`，`compatible = "xiaomi,polaris", "qcom,sdm845"` | torvalds/linux（master） |
| 引入时间 | 首个提交 `be497abe19bf`（2022-07-12，`arm64: dts: qcom: Add support for Xiaomi Mi Mix2s`）。按 tag 检查：**v6.0 起存在；v5.19 及更早（含 v5.4/v5.10/v5.15）不存在** | GitHub commit 历史 + tags 检查 |
| DTS 已覆盖（内核设备树层面） | 屏幕面板 `jdi,fhd-nt35596s`；触摸 `syna,rmi4-i2c`；蓝牙 `qcom,wcn3990-bt`；按键 `gpio-keys`；电池 `simple-battery`；PM8998/PMI8998/PM8005 RPMH 稳压器；Wi-Fi WCN3990 节点位于公共 `sdm845.dtsi` | v6.1 tag 下 DTS 内容 |
| DTS 未覆盖（需另行确认） | 相机、指纹、NFC、GPS/调制解调器、厂商音频链路、以及 Android vendor HAL 所需接口 | 同一 DTS 中未见对应节点 |

判读（不要过度解读）：

1. 主线 DTS 存在，说明"5.10+ 完全不可能"的说法不成立；但**主线支持的分界是 v6.0，不是 5.10/5.15**。
   把 5.4/5.10/5.15 当作"已有 polaris 设备树支持"的候选是错误前提。
2. 主线 DTS 只证明上游内核能枚举部分硬件，**不等于 Android 侧可用**：vendor blobs、HAL 接口、
   Android 16 所需 vendor kernel API 均未验证；相机/指纹/NFC/音频等无主线节点。
3. 因此 K2 候选格局调整：4.19（上游维护者有 bring-up 准备迹象，见 §1 表）与社区/厂商分支仍是最可能的
   中间升级路径；**v6.0+ 主线 DTS 属于研究方向**，与说明书"6.1/6.6/6.12 仅作为研究方向"一致。
4. 后续 K2-01 需要补的证据：4.19/5.4 的真实可访问内核树（含 polaris 支持）、驱动覆盖清单、
   vendor HAL 兼容性；仅有主线 DTS 不构成"候选可行"结论。

## 2. K2：候选版本评估框架

评估候选必须满足：**有可访问源码仓库 + 明确 commit**，不接受只拿到预编译镜像的方案。

| 候选 | 目标定位 | 需要确认的问题 | 状态 |
| --- | --- | --- | --- |
| Linux 4.19（CAF/上游 msm-4.19 路线） | 中间升级目标；比 4.9 新，但不是现代 GKI | 是否有可用的 SDM845 + 小米/高通代码源？驱动（相机/指纹/NFC）覆盖？设备树迁移量？上游设备树已为 4.19 bring-up 做 BT 栈下沉准备（见 §1） | **未调研**（K2-01 优先线） |
| Linux 5.4（Android common android12-5.4 等） | 更高目标的第一档 | SDM845 社区移植现状？vendor HAL 兼容性？注意：主线在 5.4 没有 polaris DTS（K0-03） | **未调研** |
| Linux 5.10+（android13-5.10 / android14-6.1 等） | 说明书首选方向 | 主线 polaris DTS 从 v6.0 才有（K0-03），5.10/5.15 均无；6.0+ 有 DTS 但缺相机/指纹/NFC 等，且 vendor HAL 未验证 | **未调研**（6.x 主线仅研究方向） |

> 说明：Android GKI 兼容矩阵只说明某个内核版本可用于某 Android 版本，**不保证**旧款 SDM845 设备的厂商驱动、
> 模块、设备树、vendor 接口可用。不得把 GKI 预编译内核直接塞给 polaris。

## 3. K2 评估判据（每项候选必须逐条填）

1. 源码仓库 URL + 分支 + commit；许可证与维护活跃度。
2. SDM845 平台支持：SoC 级代码、时钟/电源/互连、GPU、显示、音频 DSP、调制解调器。
3. 设备驱动覆盖：显示、触摸、充电、电源管理、Wi-Fi、蓝牙、音频、相机、指纹、NFC、GPS、传感器、
   休眠/唤醒、USB/ADB。
4. 模块 ABI 与 vendor 接口：Android HAL（`hardware/xiaomi`、`vendor` blob 的 ioctl/sysfs 依赖）。
5. 设备树/DTBO：polaris 的 DTS 与 sdm845-common 的差异、DTBO 编译链。
6. 编译可行性：clang 版本、内核 Makefile 与 Android 构建系统集成。
7. 风险与工作量：每项缺口的估计人日与阻塞等级。

## 4. 验收（K3/K4）

- K3：先启动，再逐项验证硬件；每项要有"通过/失败/未测"三态记录，失败要留日志。
- K4：选最终版本。若只能在 4.9 上运行 Android 16，必须标注为
  **"平台移植成功、内核升级未完成"**，不得声称内核已升级。

## 5. 下一步（K2-01 起）

1. 由方案甲/方案乙分头调研 4.19、5.4、5.10+ 的真实源码来源（记录仓库、分支、commit）。
2. 由复核官按 §3 判据做二次评估，给出"目标版本 + fallback"裁决。
3. 裁决通过后才允许创建内核分支与编译脚本（K3-01，注入官）。
