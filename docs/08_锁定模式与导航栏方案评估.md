# 08 · 锁定模式与导航栏方案评估（Phase 3 设计基线）

> 状态：**方案评估，未实现、未验证**。所有 API 行为结论都需要实机测试（T03–T09、T13）。

## 1. 需求拆解

| 需求 | 说明 | 对应验收 |
| --- | --- | --- |
| 不能离开终端 | Home / 最近任务 / 返回手势 / 应用切换都无法进入其它应用（除维护模式） | T03、T04 |
| 顶部快捷设置仍可用 | 下拉能展开快捷设置并操作 Wi-Fi / 亮度 / 蓝牙 | T06、T07、T08 |
| 隐藏底部导航 | 导航条与手势提示条隐藏 | T05 |
| 音量键正常 | 实体音量键调系统音量 | T09 |
| 管理员可维护 | 验证身份后可退出锁定 / 进维护界面 | T13 |

## 2. 方案评估顺序（必须按此顺序，避免无理由改框架）

### 方案 A：Device Owner + Lock Task（**首选**）

- 把 TerminalHome 作为 **Device Owner（DO）** 部署：应用内含 `DeviceAdminReceiver`，
  管理员通过一次性维护步骤执行
  `adb shell dpm set-device-owner org.terminalos.terminalhome/.AdminReceiver`
  （要求设备处于无账号/已恢复出厂状态，属于 **待实机验证** 的部署路径）。
- DO 能力：
  - `setLockTaskPackages(admin, [TerminalHome, com.termux])`：只允许这两个包进入锁定任务模式；
  - `setLockTaskFeatures(admin, HOME | NOTIFICATIONS | SYSTEM_INFO | QUICK_SETTINGS)`：
    - `LOCK_TASK_FEATURE_QUICK_SETTINGS`（API 28+）决定锁定模式下能否展开快捷设置；
    - `LOCK_TASK_FEATURE_OVERVIEW` 不开启 = 最近任务不可用；
    - `LOCK_TASK_FEATURE_HOME`（API 28+）决定 Home 键行为，开启时只回到允许列表内的 HOME。
  - `addPersistentPreferredActivity(...)`：把 TerminalHome 设为默认 HOME，
    从而**不需要删除系统启动器**（LineageOS 23.2 默认启动器是 `Launcher3QuickStep`）。
  - 维护出口：`clearLockTaskPackages` / `setLockTaskPackages` 置空 + PIN 校验后退出终端模式。
- 优点：全部标准 API，零框架补丁，长期可维护。
- 风险/待验证：
  1. **QUICK_SETTINGS 特性在部分 Android 版本上只允许打开快捷设置面板，二级面板（Wi-Fi 详情、蓝牙）行为可能不同** → T06/T07/T08 逐项实测；
  2. Device Owner 部署要求"设备无账号"状态，若用户已有账号需要恢复出厂；
  3. 锁定模式下通知面板行为未验证；
  4. 若 ROM 有 OTA，DO 应用需重新授权？——LineageOS 自带 ota 客户端，需实测 T14。

### 方案 A.1：已核验的关键前置——快捷设置需要 SYSTEM_SUPERVISION 角色

对 lineage-23.2 源码的只读核验（2026-10-27）结论：

1. `core/java/android/app/supervision/flags.aconfig` 定义了 aconfig flag
   `enable_lock_task_feature_quick_settings`（"Enables usage of lock task feature to enable
   Quick Settings on LockTask mode"）。
2. `LockTaskController` 在该 flag 打开时把 `LOCK_TASK_FEATURE_QUICK_SETTINGS` 映射为
   允许快捷设置（`StatusBarManager.DISABLE_NONE` / `DISABLE2_QUICK_SETTINGS`）。
3. **但** `DevicePolicyManagerService.setLockTaskFeatures()` 中：
   ```java
   boolean hasQuickSettings = (flags & LOCK_TASK_FEATURE_QUICK_SETTINGS) != 0;
   Preconditions.checkCallAuthorization(!hasQuickSettings
           || isCallerSystemSupervisionRoleHolder(caller) || isTestAdmin,
           "Caller (%s) needs to hold SYSTEM_SUPERVISION role to enable Quick Settings on LockTask mode");
   ```
   即：DPC 必须持有 `RoleManager.ROLE_SYSTEM_SUPERVISION`，否则带 QUICK_SETTINGS 位的调用会被拒绝。
4. `frameworks/base` 提供构建期配置：
   - `config_allowedSupervisionRolePackages`：分号分隔的"允许持有监督角色的包"，
     系统应用只需包名；
   - `config_systemSupervision`：默认系统监督包名；
   - `config_defaultSupervisionProfileOwnerComponent`：默认监督 Profile Owner 组件。

**决策（D-11）**：先在 ROM 层用静态 overlay 把 `org.terminalos.terminalhome` 加入
`config_allowedSupervisionRolePackages`（已写入 `vendor/terminalos/overlay/.../config.xml`），
再由 TerminalHome 在运行时通过 `RoleManager` 请求该角色（需要用户/维护入口确认），
从而**不改 frameworks/base** 就满足"锁定 + 快捷设置"。

**若该标准路径实测不可用**（角色申请失败、或被系统策略拒绝），按以下顺序考虑最小补丁：

1. `DevicePolicyManagerService.setLockTaskFeatures()`：对本 ROM 的监督应用跳过
   `isCallerSystemSupervisionRoleHolder` 检查（影响面：单个校验条件；安全影响需复核）；
2. `LockTaskController`：无条件把 QUICK_SETTINGS 映射为允许（影响面：所有锁任务场景，
   更强但更粗糙）；
3. 保留锁定 + 用受控系统设置入口替代完整快捷设置（产品体验降级，需用户确认）。

任一补丁都必须：独立提交、写清原因/影响/回滚、通过复核，并在实机跑 T06/T07/T08 后再合并。

### 方案 A.2：先跑 22.2 时的差异（重要）

lineage-22.2（Android 15）与 23.2 并不一致（已核验源码）：

| 项 | lineage-22.2 | lineage-23.2 |
| --- | --- | --- |
| `config_allowedSupervisionRolePackages` | **不存在** | 存在 |
| `enable_lock_task_feature_quick_settings` aconfig flag | **不存在** | 存在 |
| `LOCK_TASK_FEATURE_QUICK_SETTINGS` / LockTaskController 映射 | **不存在** | 存在 |
| 锁任务下"允许快捷设置"的标准 API 路径 | **不可用** | 可用（需 ROLE_SYSTEM_SUPERVISION） |

因此在 22.2 基线（当前先跑的目标）上，"锁定终端 + 顶部快捷设置可下拉"这一需求
**只能用最小框架补丁实现**，候选按影响面从小到大：

1. `services/core/java/com/android/server/wm/LockTaskController.java`：
   在锁任务状态栏禁用计算里，对可信终端应用不置位 `DISABLE2_QUICK_SETTINGS`（需要先核验 22.2
   该 flag 的具体计算路径与 setStatusBarDisabled 调用点）；
2. 若上一条会放宽所有锁任务场景，则改为只对"本 ROM 的 TerminalHome 作为锁任务持有者"的
   场景放行（需要更多上下文判断，影响面需复核）；
3. 用受控系统设置入口替代完整快捷设置（产品体验降级，需用户确认）。

补丁只能在 22.2 基线构建通过后、Phase 3 评审通过后进入代码；`vendor/terminalos` 的 22.2 分支
overlay **不包含**监督角色资源（已按版本差异适配，避免未知资源导致构建失败）。

### 方案 B：`startLockTask()` 的"屏幕固定"降级（仅作 fallback）

- 非 DO 时 `Activity.startLockTask()` 进入 pinned 模式，需要用户确认，且 Home/最近任务仍有可能退出。
- 只用于"未部署 DO 时不至于裸奔"，**不能**当作最终锁定方案。

### 方案 C：最小框架/SystemUI 补丁（仅在 A 无法满足时）

若实测证明 QUICK_SETTINGS 与"禁止退出"无法同时满足，才评估最小补丁面，候选（按从小到大的顺序）：

1. 静态 overlay 层：`config_showNavigationBar=false`（隐藏导航条，已在 vendor 仓库 overlay 中给出）；
2. SystemUI 侧：锁定任务下允许状态栏展开但禁止打开设置页（需确认具体拦截点，**未核验**）；
3. `frameworks/base` / `ActivityTaskManagerService` 侧：锁定模式下拦截非白名单 `startActivity`（影响面最大，最后手段）。

**约束**：Phase 1 基线构建成功之前，禁止修改 `frameworks/base` 与 SystemUI（说明书 §11）。
任何框架补丁必须先写设计记录（改哪个方法、为什么标准 API 不够、如何回滚）并复核。

## 3. 导航栏与手势提示条

- 隐藏导航条：`frameworks/base` 资源 `config_showNavigationBar` 置 false，通过
  `PRODUCT_PACKAGE_OVERLAYS += vendor/terminalos/overlay` 静态 overlay 生效（已在 vendor 仓库提供）。
- 手势提示条（gesture hint）：具体资源名/行为**未核验**，需要在实机上验证：
  - 若导航条隐藏后手势提示条仍在，需找对应 SystemUI 资源/配置（Phase 3 再定），不得用 `wm overscan`。
- 需求里写"如果需要保留系统手势检测，必须通过实际设备测试确认行为"——即：隐藏视觉效果与保留返回手势可能冲突，
  以实机测试结论为准（T05）。

## 4. 维护入口设计（必须有，不是可选项）

| 环节 | 设计 |
| --- | --- |
| 进入 | TerminalHome 隐藏入口（连续点击标题 7 次）→ PIN 校验 |
| PIN 存储 | PBKDF2WithHmacSHA256 + 随机 salt，仅存盐与派生值，不存明文；未设置 PIN 时不允许退出锁定 |
| 维护动作 | ① 重新拉起 Termux；② 临时退出锁定（清空 lock task 包列表）；③ 打开系统设置；④ 修改 PIN |
| 恢复默认 | 移除 DO（`dpm remove-active-admin` / 系统设置内"停用设备管理"），或恢复出厂 |
| 日志 | 记录最近失败原因、重启次数，便于排查 |

**禁止**：未验证维护入口前开启"永久锁定"（说明书 §9 第 5 条）。
