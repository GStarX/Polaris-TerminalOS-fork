# 14 · 整包构建运行手册（云端 `build-rom`）

## 1. 现状（2026-10-28，只写已核实的事实）

| 项 | 状态 | 证据 |
| --- | --- | --- |
| 22.2 云端同步 + 版本锁定 + 结构契约 | **已跑通**（GitHub 托管 runner 全绿） | run `40541735974`，见 docs/13 |
| 整包 `build-rom` | **从未在真实大 runner 上执行** | 无运行记录 |
| 本机构建 | **不做**（用户要求：构建只在云端） | — |
| 硬阻塞 | 需 ≥400 GB 可用磁盘 / ≥32 GB RAM / ≥8 核 runner | 托管标准 runner 约 14 GB，preflight 立即失败 |

## 2. 跑之前的 5 项就绪检查

1. **runner 已注册**：仓库 `Settings → Actions → Runners` 状态为 `Idle`，label 含 `self-hosted,linux,x64` 和自定义 label（如 `lineage-builder`）。
2. **大磁盘就是构建卷**：preflight 量的是 workspace 所在卷（`$GITHUB_WORKSPACE/android`，未创建时退回 `$GITHUB_WORKSPACE`）。若大磁盘挂在 `/mnt/build`，必须让 runner 的 `_work` 目录落在那块盘上，否则会误判为磁盘不足。
3. **内存 ≥32 GB**：低于 32 GB preflight 只 WARN 不拦，但整包很可能 OOM，不建议硬上。
4. **ccache 目录跨运行保留**：`$HOME/.ccache` 在 self-hosted 上默认保留，首次构建后二次构建显著提速。
5. **网络撑得住全量 sync**：整包 sync 量级远大于 sync-check（后者在托管 runner 上曾耗时约 13 分钟且出现波动）；workflow 已内置 3 次重试，链路太差仍会失败。

## 3. 第一次跑：参数怎么填

`Actions → build-rom → Run workflow`，**先基线、后产品**，不要跳步：

| 次序 | `lineage_branch` | `build_target` | `runner` | 目的 |
| --- | --- | --- | --- | --- |
| 1 | `lineage-22.2` | `baseline` | `["self-hosted","linux","x64","lineage-builder"]` | 证明构建链 + 设备树/内核/blobs 组合能编过（不含 TerminalOS 改动） |
| 2 | `lineage-22.2` | `terminalos` | 同上 | 加 Termux 预置 + TerminalHome + overlay |

- `runner` 是 JSON：self-hosted 填数组 `["self-hosted","linux","x64","lineage-builder"]`（按真实 label 改）；GitHub larger runner 填字符串，如 `"ubuntu-24.04-64core"`。填错在 job 启动阶段就报 `No runner matching labels`，不会启动构建。
- `ccache` 保持 `true`；`release_tag` 首次留空（先确认产物再发布）。
- `baseline` 只支持 `lineage-22.2`（23.2 缺内核/blobs 分支），workflow 会显式报错退出。

## 4. 时间预算与超时口径

| 阶段 | 8 核 / 32 GB | 16 核 / 64 GB |
| --- | --- | --- |
| 依赖安装 + repo init | 5–10 分钟 | 5–10 分钟 |
| 全量 `repo sync`（首次） | 40–120 分钟 | 40–120 分钟 |
| 整包编译（首次，无 ccache 命中） | 4–8 小时 | 2.5–5 小时 |
| 二次构建（ccache 命中） | 约减半或更多 | 同左 |

- **GitHub 托管 runner 单 job 上限 6 小时（360 分钟）**；self-hosted 不受这一条限制，但 `build-rom.yml` 的 `timeout-minutes: 900` 是工作流侧硬上限。
- 8 核首次构建很可能超过 6 小时：用托管 larger runner 优先 16 核以上；用 self-hosted 注意 900 分钟是否够。
- 超时的表现是 job 被强制终止、**没有产物**，日志停在编译中途——这不是编译错误；self-hosted 上 `out/` 保留时重跑会增量继续。

## 5. 失败分诊（按报错位置查）

| 失败位置 | 典型信息 | 处理 |
| --- | --- | --- |
| preflight | `可用磁盘 N GB < 最低要求 350 GB` | runner 选错或磁盘挂错卷，见 §2 第 1、2 项 |
| job 启动 | `No runner matching labels` | `runner` 输入与 runner 实际 label 不一致 |
| `repo init` / `repo sync` | `fatal: cannot obtain manifest`、网络超时 | 已自动重试 3 次；仍失败是链路问题，换网络/代理，不要靠放宽检查绕过 |
| `fetch-vendor-deps` | 缺依赖、分支不匹配 | 检查 `--target-branch` 与 docs/01 的锁定关系 |
| Termux 校验 | `sha256sum --check` 失败 | APK 版本被上游改动；`vendor/terminalos` 的版本与 sha256 要同步更新（改版本走 docs/11 决策） |
| `lunch` | `Invalid lunch combo` | 产品名错或产品未注册；baseline 用 `lineage_polaris`，terminalos 用 `terminalos_polaris` |
| 编译中 | 缺头文件/缺库、`ninja: build stopped` | 真实编译问题；先看 `out/ci/build.log` 尾部，别盲目重跑 |
| 产物收集 | `没有找到可刷写 ROM 包` | 只产出了中间产物（target_files），说明 bacon/ota 没跑完；看 build.log |

## 6. 产物验收

1. artifact `rom-<branch>-<target>` 里应有 `lineage-*-UNOFFICIAL-polaris.zip`（可刷写包）+ 各 `*.img` + `sha256sums.txt` + `build-info.txt`。`target_files` 等中间 zip 已被排除，不再混进 artifact。
2. `build-info.txt` 必须对得上：branch、product、target、run_id，以及 6 个仓库的实际 commit。
3. `sha256sums.txt` 的值要在下载后本地重算比对（不信任传输）。
4. 产物是 AOSP test-key 测试签名，**不外发、不用于正式发布**。
5. 真机刷写**只由首席执行**；本仓库脚本与 CI 不含任何刷机命令。

## 7. 运行记录写在哪

- CI 自动写：`ci-status` 分支 `runs/<时间戳>-build-rom.json`（状态、分支、run 链接）。
- 人工记录：追加到 [`docs/13`](./13_首次云构建记录.md) 的"Run N"小节，格式同已有条目——run id、commit、通过/失败的步骤、真实原因。**没真跑过就不写"已通过"。**

## 8. 明确不做的事

- 不在本机（Windows）构建，也不用群晖顶替（docs/12 §2 方案 C）。
- 不为"变绿"放宽 preflight 门槛：磁盘不足就是不足，硬编只会把失败推迟几小时。
- 不改 `validate.yml` 的检查项来绕过失败。
