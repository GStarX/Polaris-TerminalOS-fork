## 1. 硬规则（先读）

1. **没有记录 = 没有完成。** 构建、产物、验证结论都必须能由记录复现；口头/聊天里的"成功了"不算。
2. **不得虚构。** 没有代码提交、没有构建、没有实机测试，就分别写"未构建 / 未验证 / 未测试"。
3. **失败也要记录。** 失败构建同样是交付物（尤其 docs/03 P1-12：23.2 的失败点分类），必须写清失败命令、首个错误、日志路径。
4. **不得代填。** 真机测试结果只能由**首席**记录；其他角色只能准备材料与判据（docs/04 §3）。
5. **一条记录对应一次构建。** 同一次构建的不同产物/不同测试在这条记录里引用，不拆成多条。
6. **可复现三要素**：源码 commit + 构建命令 + 构建环境，缺一不可。
7. **产物必须可校验**：记录文件名 + 大小 + **sha256**；sha256 以 `out/artifacts/<时间戳>/sha256sums.txt` 为准。
8. **构建成功 ≠ 验证通过。** 只有实机测试（T01–T15）通过并记录，才能写"验证通过"。

## 4. 状态定义（唯一合法取值）

| 状态 | 含义 | 允许的表述 |
| --- | --- | --- |
| `未执行` | 该步骤根本没运行 | "未执行/未验证" |
| `进行中` | 正在运行，尚无结论 | 记录开始时间、预计时长 |
| `失败` | 命令非零退出或产物校验失败 | 必须附失败日志路径与首个错误 |
| `产物已生成（未验证）` | 构建命令成功、产物存在且 sha256 已记录 | **只能**写"构建产物已生成，未经实机验证" |
| `验证通过` | 实机测试项通过并有证据（仅首席可记） | 必须引用具体测试编号与证据 |
| `阻塞` | 环境/依赖/上游限制导致无法继续 | 写明阻塞原因与解除条件 |

**禁止写法**（除非确有证据，否则一律不许）：

- "已构建成功"（没有 commit + 命令 + 产物 sha256 时）；
- "已测试通过" / "功能正常"（没有实机测试编号与证据时）；
- "应该没问题" / "理论上可行" 作为结论；
- "官方支持 23.2"（docs/00 已核实：官方支持截止 22.2）。

## 5. 产物收集与校验（脚本对应）

| 动作 | 脚本/命令 | 产出文件 |
| --- | --- | --- |
| 基线构建 | `scripts/build-baseline.sh` | `out/baseline-artifacts.txt`（产物名 + 大小） |
| TerminalOS 构建 | `scripts/build-terminalos.sh` | `out/terminalos-artifacts.txt`（含 Termux sha256、产物名 + 大小） |
| 产物收集 + 校验 | `scripts/collect-artifacts.sh` | `out/artifacts/<UTC 时间戳>/` 下的产物、`sha256sums.txt`、`build-info.txt` |
| 人工复核 | `sha256sum <文件>`、对照 `sha256sums.txt` | 记录"复核一致" |

说明：

- `collect-artifacts.sh` 每次创建**新的时间戳目录**，不覆盖历史目录；
- `build-info.txt` 自动记录各仓库 `git log -1 --oneline`、Build ID、构建日期等，可直接粘贴进 §3 模板；
- 建议把构建日志同时保存到构建机 `out/logs/<记录编号>.log`，并在记录中写出路径（**日志不得删除**）。

## 8. 归档与保留建议

- 产物目录名用 UTC 时间戳，天然唯一；**不要手工覆盖或改名**已归档目录。
- 每个发布候选版本保留：产物 + `sha256sums.txt` + `build-info.txt` + 构建日志 + 本条构建记录。
- 构建机空间不足时，先归档到项目外存储再清理 `out/`，清理前确认 sha256 已记录。
- 历史上游/依赖变化时（例如内核或 blobs 出现 23.2 分支），在记录中引用对应 docs/00 的重新核验结论，不修改旧记录。
